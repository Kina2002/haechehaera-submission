## 먼저 알아 둘 말

| 말 | 뜻 |
|---|---|
| 명세(SPEC) | 게임이 어떻게 동작하는지 적은 설명서입니다. |
| Markdown | `#`, `-` 같은 기호로 제목·목록·표를 쓰는 글 형식입니다. GitHub가 보기 좋게 바꿔 보여 줍니다. |
| 커밋 · PR | 커밋은 바뀐 내용 한 묶음을 이력에 남기는 일입니다. PR(Pull Request)은 그 묶음을 기준 가지(main)에 합치기 전에 검토하는 요청입니다. |
| 줄 끝 형식 | 줄이 끝났다는 보이지 않는 표시입니다. Windows식은 CRLF, 다른 곳은 LF를 씁니다. 눈에는 같아도 Git은 다른 줄로 봅니다. |
| 이스케이프 | 기호 앞에 `\`를 붙여 "기능 말고 글자로 보여 달라"고 하는 표시입니다. |

## F와 P 규칙

2026-10-08부터 이렇게 써 왔고, 2026-11-09 참가자의 질문을 계기로 규칙으로 정리했습니다.

- **F 문서**는 지금 게임에 있는 기능입니다. 본문은 코드와 맞춥니다. 아직 게임에 없는 계획은 본문을 바꾸지 않고 맨 아래 "개발 참고"에 링크 한 줄만 답니다. 예: [F19](../../구현/해체해라-2026-10-07-v01/문서/SPEC-기능별-2026-10-07-v01/F19-자금-입장료와-경기-결산.md)의 "향후 구상: P19 리그별 수입".
- **P 문서**는 아직 게임에 없는 계획입니다. 확정(참가자 결정)·제안·미정을 나눠 적고, 맨 위에 상태를 씁니다. 예: "향후 추가 희망 · 미구현", "기획 중 · 미구현", "결정(2026-11-10) · 미구현 · 숫자는 시험값", "시험 기록 · 게임 규칙 변경 없음".
- **계획을 게임에 넣으면** F 본문을 고치고 P에 "구현 완료"를 표시합니다. 예: [P04 경기 기록 색상](../../구현/해체해라-2026-10-07-v01/문서/SPEC-기능별-2026-10-07-v01/P04-경기-기록-구분과-색상.md)은 2026-10-08 구현 뒤 "구현 완료"로 바꾸고, F14에 적용 규칙과 P04 링크를 넣었습니다. 일부만 넣은 [P07 업적 확장](../../구현/해체해라-2026-10-07-v01/문서/SPEC-기능별-2026-10-07-v01/P07-업적-확장.md)은 "선택 항목 구현 완료, 구원투수 후보 보류"로 남겼습니다.
- **향후 구상 목록**에는 P 문서 한 줄 요약과 "게임에 넣는 순서"(2026-11-10 참가자 결정)를 둡니다.

## 돌아보며

- 문서를 "지금 있는 것(F)"과 "앞으로 할 것(P)"으로 나누면, 기획이 바뀌어도 지금 게임 설명이 흔들리지 않습니다.
- 한 문서에는 한 주제만 둡니다. 길어지면 결정과 시험 기록을 다른 곳으로 나눕니다.
- 남이 만든 파일을 고칠 때는 줄 끝 형식을 그대로 두고, 올리기 전에 "추가한 줄만 바뀌었는지" 확인합니다.
- GitHub Markdown에서 범위는 `\~`로 씁니다.
- 생성 스크립트로 만든 문서를 손으로 고치기 시작하면, 어느 쪽이 원본인지 적어 둡니다.
- 문서 개수나 작성일을 적은 문장은 문서가 바뀔 때 같이 고칩니다.
